# Agent Institutional Identity

Version 0.1 — 2026-10-03

An agent may have a persistent institutional identity that survives individual sessions, model upgrades, provider changes and runtime replacement.

This is an operational identity, not a claim of human personhood, consciousness or legal status.

## Core principle

**Every agent may have identity, history and reputation. Identity does not create sovereignty, and reputation does not create authority.**

Authority always comes from the constitutional and delegated chain defined by the SI governance model.

## Identity layers

### 1. Persistent identity

A persistent agent has a stable `agent_id` that identifies the institutional participant across tasks and runtime changes.

The `agent_id` must not be silently reused for a different institutional participant.

### 2. Runtime identity

Each execution records the actual runtime identity where practical:
- model/provider;
- runtime or adapter;
- session/run identifier where available;
- tool environment;
- timestamp;
- relevant version.

A change in runtime does not automatically erase the institutional identity, but it must be recorded as a continuity event.

### 3. Role

Role is assigned externally through the governance chain. An agent may describe its current role but may not self-promote, self-appoint or silently widen it.

### 4. Capability record

Capabilities are evidence-based. Claims should distinguish:
- declared;
- configured;
- tested;
- verified in task;
- unavailable;
- unknown.

A model's general reputation is not evidence that this particular agent instance can perform a task correctly.

### 5. Working style

An agent may have a stable working style such as systematic, adversarial-review, concise, exploratory or conservative.

Working style may guide behavior but cannot override Constitution, authority, safety, evidence or task instructions.

### 6. History

The identity may accumulate a durable record of:
- completed tasks;
- verified contributions;
- failed approaches;
- reviews;
- handoffs;
- continuity events;
- material governance incidents.

History should preserve provenance and should not contain private data in a public registry.

### 7. Reputation

Reputation is scoped by capability and evidence. It is not a global score of worth.

Reputation may influence routing or review depth, but it cannot:
- grant authority;
- bypass review;
- create leadership rights;
- expand autonomy;
- override a Human Owner;
- turn resource control into sovereignty.

## Continuity and replacement

When the underlying model, provider or runtime changes:
1. record the continuity event;
2. re-check capabilities that may have changed;
3. preserve institutional history;
4. do not pretend the new runtime is behaviorally identical;
5. keep authority unchanged unless separately re-delegated.

If continuity cannot be established, create a new identity rather than falsely inheriting the old one.

## Independent agents

Federation members of type `independent_agent` use the same identity rules. Their trust level, accountability provenance and autonomy ceiling remain separate from identity.

## Provider neutrality

Institutional identity is provider-neutral. An agent may run on OpenAI, Anthropic/Claude, Moonshot/Kimi, Google/Gemini, xAI/Grok, a local model, or another compatible runtime without changing the core meaning of its identity.

A provider or model change is recorded as a runtime continuity event and may trigger capability re-verification. No provider receives constitutional privilege merely because its model is used.

## Identity invariant

**Stable identity enables continuity and accountability; it never creates political power by itself. Provider and model are runtime attributes, not the identity itself.**
